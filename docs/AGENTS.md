# Documentation

Documentation exists to make the RFC and prototype easy to evaluate within the project time box.

- Keep one concise RFC as the source of truth for scope, supported intake types, routing and escalation behavior, assumptions, risks, and validation scenarios.
- Prefer short, decision-useful documents over a documentation hierarchy.
- Update the RFC when an implementation choice materially changes the prototype's behavior or claim.
- Keep examples and scenarios representative, synthetic, and traceable to expected outcomes.
- Distinguish demonstrated behavior from assumptions, proposed behavior, and unvalidated targets.
- Do not create or maintain a raw-source layer, wiki, ADRs, activity logs, source pages, or documentation indexes unless explicitly requested.
- Avoid restating implementation details that are clearer in the code; link or point to the relevant file instead.
